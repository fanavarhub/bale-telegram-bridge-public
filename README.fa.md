# پل خصوصی بله و تلگرام

این پروژهٔ متن‌باز Node.js پیام‌های خصوصی دو حساب را بین یک ربات بله و یک ربات تلگرام منتقل می‌کند. هویت‌های واقعی فقط در فایل محلی `.env` تنظیم می‌شوند و در کد عمومی پیش‌فرضی ندارند:

| سرویس | ربات مورد انتظار | تنها شناسهٔ مجاز |
|---|---|---|
| بله | `BALE_BOT_USERNAME` | `BALE_ALLOWED_USER_ID` |
| تلگرام | `TELEGRAM_BOT_USERNAME` | `TELEGRAM_ALLOWED_USER_ID` |

نسخهٔ عمومی هیچ شناسهٔ شخصی یا نام ربات واقعی در کد ندارد. اطلاعات آزمون ساختگی‌اند. **اتصال زنده، مالکیت ربات‌ها و درستی شناسه‌های تنظیم‌شده بدون توکن تأیید نشده‌اند.** توکن‌ها را فقط روی سرور خودتان وارد کنید؛ نیازی به فرستادن آن‌ها در چت نیست. بررسی مستندات، مقایسه با راه‌حل‌های مشابه و پیشنهاد شبکه در [گزارش فارسی](./RESEARCH.fa.md) آمده است.

## رفتار برنامه

- متن فارسی، لینک و ایموجی معمولی به‌صورت متن ساده؛ نشانه‌گذاری HTML/Markdown تفسیر نمی‌شود.
- عکس، ویس، صوت، ویدئو، انیمیشن و سند با دانلود از مبدأ و بارگذاری مجدد در مقصد. فایل در سرور اجرا یا تبدیل نمی‌شود.
- اگر سرویس قالب یک فایل را نپذیرد، یک بار ارسال همان بایت‌ها به شکل سند امتحان می‌شود.
- ویدئوی دایره‌ای به ویدئوی معمولی و استیکر به فایل تبدیل می‌شود. آلبوم به پیام‌های جدا تبدیل می‌شود.
- نظرسنجی، تاس و اطلاعات بازی به متن تبدیل می‌شوند؛ تعامل و نتیجه‌های بعدی همگام نمی‌شوند.
- مخاطب و موقعیت ثابت منتقل می‌شوند؛ vCard به متن و موقعیت زنده به نقطهٔ ثابت تبدیل می‌شود.
- پاسخ به پیام با نگاشت شناسه‌ها در صورت موجودبودن حفظ می‌شود. اگر نگاشت موجود نباشد یا مرجع حذف شده باشد، محتوا بدون ارجاع فرستاده می‌شود.
- ویرایش، پیام تازه با برچسب ویرایش می‌سازد. حذف، واکنش، تماس، رسید خواندن و وضعیت آنلاین همگام نمی‌شوند.
- محتوای محافظت‌شده، عکس زندهٔ ترکیبی و نوع ناشناخته منتقل نمی‌شوند و فرستنده اعلان می‌گیرد.
- پیام گروه، کانال، حساب سوم، بات و زمینهٔ تجاری/مهمان پذیرفته نمی‌شود؛ به فرستندهٔ غیرمجاز پاسخی داده نمی‌شود.

سقف برنامه **۲۰ MiB، برابر ۲۰٬۹۷۱٬۵۲۰ بایت** است و می‌توانید آن را کمتر کنید. این عدد تضمین پذیرش سرویس نیست؛ مرز واقعی اندازه و قالب باید آزمایش شود. عکس بزرگ‌تر از ۱۰ MiB به شکل سند ارسال می‌شود. اگر فراداده اندازه را نگوید، شمارش واقعی بایت‌های دانلودشده سقف را اعمال می‌کند. فایل بزرگ‌تر رد می‌شود و فرستنده اطلاع می‌گیرد. راه انتقال فایل‌های بزرگ در این نسخه، تقسیم آن توسط فرستنده و ارسال چند فایل کوچک‌تر است؛ تقسیم خودکار پیاده نشده است.

## معماری و قطعی

```text
حساب مجاز بله → API بله → دریافت مستقل → SQLite رمزگذاری‌شده → API تلگرام → حساب مجاز تلگرام
حساب مجاز تلگرام → API تلگرام → دریافت مستقل → SQLite رمزگذاری‌شده → API بله → حساب مجاز بله
```

پیشنهاد شروع، یک VPS همیشه‌روشن خارج از ایران با دسترسی مستقیم HTTPS به هر دو API است؛ اتصال همان میزبان به بله و مسیر فایل آن را ابتدا با ابزار زیر بسنجید. منطقهٔ جغرافیایی به‌تنهایی تضمین اتصال نیست. دامنه، پورت ورودی، گواهی عمومی، webhook و نصب کلاینت بله روی دستگاه شما لازم نیست. نسخهٔ فعلی تک‌سروره است؛ جمع‌آورندهٔ داخل ایران یا failover دو سروره پیاده نشده است.

دریافت، ذخیرهٔ فایل و ارسال در هر جهت مستقل‌اند. ابتدا پیام و offset در یک تراکنش ذخیره می‌شوند؛ درخواست بعدی دریافت، آن‌ها را تأیید می‌کند. فایل دریافت‌شده نیز به‌صورت رمزگذاری‌شده ذخیره می‌شود، حتی وقتی مقصد قطع است. تا پیش از موفقیت دانلود فایل، فقط اطلاعات پیام در صف وجود دارد؛ بایت‌های هنوز دریافت‌نشده را نمی‌توان تضمین کرد. ترتیب انتقال محتوا در هر جهت حفظ می‌شود؛ کمک و وضعیت محلی می‌توانند از صف مقصد قطع‌شده عبور کنند.

برای خطای شبکه، خطای موقت سرویس و محدودیت نرخ، تلاش با تأخیر افزایشی انجام می‌شود و `retry_after` رعایت می‌شود. اگر دریافت‌کننده ربات را شروع نکرده یا مسدود کرده باشد، خطای ۴۰۳ باعث نگه‌داشتن پیام و تلاش مجدد می‌شود و مبدأ اعلان می‌گیرد. خطای دائمی پیام/فایل پس از مسیر جایگزین، شکست ثبت می‌کند و به فرستنده اطلاع می‌دهد؛ در این حالت باید پیام را دوباره بفرستد. دستور وضعیت، تضمین خواندن پیام نیست.

**تضمین انتقال دقیقاً یک بار وجود ندارد.** اگر مقصد پیام را بپذیرد اما پاسخ HTTP یا ثبت محلی بعدی قطع شود، تلاش مجدد ممکن است نسخهٔ تکراری بسازد. checkpoint هر قسمت پیام و حذف‌نکردن صف در restart این خطر را کاهش می‌دهد. هر ربات فقط یک گیرندهٔ polling داشته باشد. قفل محلی برنامه برای جلوگیری از اجرای همزمان اشتباهی است؛ سازوکار HA و قفل توزیع‌شده نیست.

صف، قطعی کامل بین‌الملل را رفع نمی‌کند. فقط آنچه به سرور رسیده محفوظ است؛ پیام‌های هنوز دریافت‌نشده و فایل‌های هنوز دانلودنشده تابع محدودیت و ماندگاری خود سرویس‌اند. نگهداری سمت سرویس محدود است؛ قطعی طولانی می‌تواند به ازدست‌رفتن پیام‌های دریافت‌نشده منجر شود. محدودیت دقیق مستند در گزارش آمده است.

## راه‌اندازی بدون Docker

نیاز: Node.js نسخهٔ ۲۴ یا بالاتر، یک دیسک محلی ماندگار و مسیر خروجی HTTPS روی پورت ۴۴۳. هیچ بستهٔ npm ثالثی لازم نیست و `npm install` نیاز نیست. `node:sqlite` ممکن است در بعضی نسخه‌های Node هشدار آزمایشی بدهد.

روی سرور لینوکسی، پوشهٔ پروژه را باز کنید:

```bash
cp .env.example .env
chmod 600 .env
npm run key --silent
```

خروجی دستور آخر را **یک بار** در `DATA_ENCRYPTION_KEY` بگذارید. توکن و نام کاربری هر ربات و شناسهٔ عددی کاربر مجاز همان سمت را در متغیرهای متناظر `.env` وارد کنید. `BALE_ALLOWED_USER_ID`، `TELEGRAM_ALLOWED_USER_ID`، `BALE_BOT_USERNAME` و `TELEGRAM_BOT_USERNAME` الزامی‌اند؛ بدون آن‌ها برنامه شروع نمی‌شود. برای ویرایش از ویرایشگر محلی سرور استفاده کنید؛ توکن را در آرگومان command یا history شل نگذارید. کلید را با هر restart دوباره نسازید؛ کلید اشتباه، پایگاه قبلی را باز نمی‌کند.

در PowerShell به‌جای دو دستور اول:

```powershell
Copy-Item .env.example .env
npm run key --silent
```

مجوز فایل‌های secret را با ACL ویندوز به حساب اجرای برنامه محدود کنید. اجرای دائمی روی Linux/VPS توصیه می‌شود.

`from.id` هر کاربر مجاز از تنظیمات محلی هنگام شروع خوانده و برای اجرای همان فرایند ثابت می‌شود. تنها یک کاربر در هر سرویس مجاز است و ثبت خودکار اولین فرستنده وجود ندارد. شناسهٔ چت خصوصی بله به‌صورت پیش‌فرض از `BALE_ALLOWED_USER_ID` گرفته می‌شود؛ مستند بله برابری شناسهٔ چت خصوصی و کاربر را صریح تضمین نمی‌کند. برای بررسی اولیه، **پل را متوقف نگه دارید**، از هر حساب مجاز Start بفرستید و اجرا کنید:

```bash
npm run doctor -- --private-chat --samples=1
```

فقط شناسهٔ چت خصوصیِ پیام‌هایی که فرستندهٔ همان کاربر مجاز دارند نمایش داده می‌شود؛ متن و شناسهٔ دیگران چاپ نمی‌شود. اگر شناسهٔ بله متفاوت بود، همان مقدار تأییدشده را محلی در `BALE_PRIVATE_CHAT_ID` پین کنید. این تنظیم، شناسهٔ کاربر مجاز را تغییر نمی‌دهد؛ هر دو بررسی کاربر و چت خصوصی همچنان الزامی‌اند. این عیب‌یابی را همزمان با پل/گیرندهٔ قبلی اجرا نکنید. در صورت webhook فعال، ابتدا با روال جایگزینی پایین آن را کنار بگذارید و Start تازه بفرستید.

قبل از اجرا، هر دو نفر با حساب مجاز خود ربات همان سمت را Start کنند. نام کاربری ربات با شناسهٔ عددی کاربر فرق دارد. شناسه‌ها باید دقیقاً شناسهٔ حساب در همان سرویس باشند؛ تلفن، شناسهٔ ربات یا نام کاربری جایگزین آن نیست.

```bash
npm test
npm run doctor
npm start
```

پس از اتصال، `/start` و `/help` راهنما و `/status` آمار صف همان سمت را نشان می‌دهند. این سه دستور محلی هستند و به طرف دیگر فرستاده نمی‌شوند. متن و فایل عادی مستقیماً به طرف مقابل می‌روند.

اگر bot دیگری روی همین توکن webhook دارد، برنامه با خطای روشن متوقف می‌شود. پس از کنارگذاشتن برنامهٔ قبلی، خودتان در `.env` مقدار `REMOVE_EXISTING_WEBHOOK=true` بگذارید تا webhook حذف شود؛ درخواست حذف، دورریختن عمدی پیام‌های معوق را نمی‌خواهد. همزمان‌بودن گیرندهٔ دیگر همچنان باعث conflict می‌شود. از توکن مشترک با سرویس قبلی استفاده نکنید مگر سرویس قبلی را متوقف کرده باشید.

## اجرا با Docker Compose

برای اجرای مستقیم با PM2، [دستورهای کامل نصب و اجرای PM2](./deploy/PM2.fa.md) و `ecosystem.config.cjs` آماده‌اند. فایل `.env` روی سرور می‌ماند و فقط یک پردازش fork اجرا می‌شود. یکی از PM2، Docker یا systemd مستقیم را انتخاب کنید.

پس از تکمیل `.env`، روی Linux:

```bash
mkdir -p data
sudo chown 1000:1000 data
chmod 700 data
docker compose up -d --build
docker compose logs --tail=50 -f
```

محیط و دادهٔ کانتینر از پوشهٔ پروژه جدا نمی‌شوند؛ volume داده را حفظ کنید. فایل `.env` داخل image کپی نمی‌شود. متغیرهای محیطی برای مدیر سرور/Docker قابل‌دسترسی‌اند. برای به‌روزرسانی image، طبق روال خودتان build مجدد کنید. Docker در این محیط اجرا و تأیید نشده است؛ قبل از استقرار نهایی روی میزبان آزمایش کنید.

برای تست در همان کانتینر:

```bash
docker compose run --rm bridge node src/doctor.js
docker compose run --rm bridge node src/queue.js status
```

برای اجرای مستقیم دائمی، نمونهٔ [systemd](./deploy/bridge.service) موجود است. مسیر `node` و پوشهٔ پروژه را با سرور تطبیق دهید؛ حساب سیستم `bridge` بسازید، پوشهٔ `data` را در اختیار آن قرار دهید و `.env` را فقط برای آن قابل‌خواندن کنید. فقط **یکی** از Docker یا systemd را اجرا کنید. health صرفاً روشن‌بودن فرایند نیست؛ موفقیت API، سن صف و فضای دیسک را هم پایش کنید.

## سنجش اتصال از سرور نهایی

بدون توکن و بدون `.env`، DNS، TLS و دسترسی HTTP را بسنجید:

```bash
node src/doctor.js --public --samples=5 --interval=10
```

با `.env` تکمیل‌شده، تطبیق ربات و وضعیت webhook هم بررسی می‌شود:

```bash
npm run doctor -- --samples=60 --interval=60
```

ابزار doctor در حالت معمول هیچ پیام یا `getUpdates` نمی‌فرستد و webhook را حذف نمی‌کند. تنها گزینهٔ صریح `--private-chat`، با پل متوقف، دریافت بدون تأیید شناسه‌های مثبت را برای تشخیص چت انجام می‌دهد. خروجی JSON فقط متادیتای تشخیصی دارد. پاسخ ۴۰۴ ریشهٔ دامنه هم می‌تواند نشانهٔ دسترسی HTTP باشد؛ سلامت API احرازشده یا دانلود/آپلود فایل را ثابت نمی‌کند. سنجش DNS/TLS از اتصال مستقیم همین میزبان است و پروکسی را به‌عنوان طرح استقرار آزمایش نکرده‌ایم.

برای آزمون دانلود، شناسهٔ یک فایل کوچک و غیرحساس متعلق به **همان ربات در همان سرویس** را روی سرور در متغیرهای محلی زیر قرار دهید:

```dotenv
DIAGNOSTIC_BALE_FILE_ID=
DIAGNOSTIC_TELEGRAM_FILE_ID=
```

```bash
npm run doctor -- --media --samples=3 --interval=10
```

نیازی به فرستادن شناسه یا توکن در چت نیست. شناسه را از پاسخ API ابزار خودتان به دست بیاورید؛ ابزار دریافت دوم را همزمان با پل اجرا نکنید. این تست دانلود را می‌سنجد؛ تست بارگذاری با ارسال دوطرفهٔ واقعی انجام می‌شود. ۴۸ تا ۷۲ ساعت سنجش از میزبان نهایی و شبکهٔ واقعی ایران، از یک تست موفق مفیدتر است. ابزار به‌طور خودکار سرور یا کشور «بهترین» انتخاب نمی‌کند.

## صف، پشتیبان و حریم خصوصی

```bash
npm run queue -- status
npm run queue -- backup ./backup.sqlite
```

دستور وضعیت تعداد کارها، سن قدیمی‌ترین کار، حجم فایل‌های رمزگذاری‌شده و offsetها را نشان می‌دهد؛ متن، نام فایل و توکن نمایش داده نمی‌شود. snapshot با SQLite گرفته می‌شود؛ کپی‌کردن فقط `bridge.sqlite` هنگام اجرای برنامه، تغییرات WAL را لزوماً شامل نمی‌شود. مقصد پشتیبان نباید از قبل وجود داشته باشد. پشتیبان را از پوشهٔ سرور به محل امن خودتان منتقل و دسترسی آن را محدود کنید.

بازیابی: برنامهٔ قبلی را متوقف کنید، **کل پوشهٔ دادهٔ فعلی را امن کنار بگذارید**، پوشهٔ دادهٔ خالی بسازید و snapshot را در آن با نام `bridge.sqlite` قرار دهید؛ کلید قبلی را استفاده کنید. فایل‌های `-wal` و `-shm` پایگاه قدیمی را با snapshot مخلوط نکنید. مجوزها را اصلاح کنید و برای انقضای lease قدیمی تا ۶۰ ثانیه صبر کنید. فقط یک نمونه را روشن کنید. نسخهٔ پشتیبان قدیمی، تحویل‌های بعد از زمان snapshot را بازسازی نمی‌کند و بازیابی قدیمی ممکن است تکرار یا شکاف ایجاد کند.

متن، برنامهٔ ارسال و بایت فایل با AES-256-GCM و کلید ۳۲ بایتی رمزگذاری می‌شوند. نام و اندازهٔ برخی موجودیت‌های صف، شناسهٔ پیام‌ها، شمارنده‌ها و زمان‌ها متادیتای SQL هستند؛ محتوای پیام نیستند. محتوای کار تکمیل‌شده/شکست‌خورده حذف می‌شود؛ نگاشت پاسخ و متادیتای پایان‌یافته به‌طور پیش‌فرض ۷ روز باقی می‌مانند. **کار معوق خودکار پس از ۷ روز حذف نمی‌شود.** فایل SQLite ممکن است بعد از تخلیه کوچک نشود، چون صفحات را برای استفادهٔ بعدی نگه می‌دارد.

صف به تعداد `MAX_PENDING_JOBS` محدود است؛ در پرشدن، فقط پیشوندی که واقعاً ذخیره شده تأیید می‌شود. باقی پیام‌ها تا فراهم‌شدن ظرفیت در سرویس می‌مانند و ممکن است به مهلت نگهداری آن برسند. حد تعداد، سهمیهٔ حجمی دیسک نیست: ده‌هزار فایل ۲۰ MiB تقریباً ۲۰۰ GiB جا می‌خواهد. برای دو نفر مقدار کمتری تنظیم و فضای آزاد را پایش کنید. پرشدن/خطای دیسک باعث توقف برنامه می‌شود؛ ابتدا ظرفیت را اصلاح کنید. فایل SQLite روی NFS، پوشهٔ همگام‌شونده یا دیسک موقت کانتینر قرار نگیرد.

این سامانه E2EE نیست: دو پیام‌رسان و سرور در زمان اجرا محتوا را می‌بینند. رمزگذاری صف از مدیر سروری که کلید یا حافظهٔ فرایند را دارد پنهان نمی‌کند. از VPS و حساب مدیریتی قابل‌اعتماد استفاده کنید. لاگ برنامه فقط دستهٔ خطا و شناسهٔ کار را می‌نویسد؛ proxy/debug لاگ‌گیر خودتان هم نباید URL کامل حاوی توکن را ذخیره کند. پیام تأییدشدهٔ مقصد به معنی خواندن انسان نیست.

پایگاه داده به هویت‌های تنظیم‌شده وابسته است. تغییر کاربران، چت‌ها یا نام ربات‌ها روی همان پایگاه با خطا متوقف می‌شود تا پیام‌های قدیمی به مقصد تازه نروند؛ شناسهٔ واقعی بات از `getMe` هم ثبت و در اجراهای بعدی بررسی می‌شود. برای تغییر طرفین از مسیر دادهٔ تازه پس از رسیدگی به صف قبلی استفاده کنید و پایگاه قدیمی را برای دورزدن خطا حذف نکنید. تعویض توکن همان ربات مجاز است. پایگاه قدیمیِ دارای سابقه از نسخه‌های بدون این اتصال هویت، مستقیم پذیرفته نمی‌شود؛ ابتدا صف را با نسخهٔ قبلی تخلیه، آن را متوقف و پایگاه و کلید را پشتیبان بگیرید، سپس نسخهٔ عمومی را با `DATA_DIR` تازه اجرا کنید.

## تنظیمات و خطاها

| متغیر | پیش‌فرض | کاربرد |
|---|---|---|
| `BALE_BOT_TOKEN` / `TELEGRAM_BOT_TOKEN` | الزامی | فقط secret محلی |
| `BALE_ALLOWED_USER_ID` / `TELEGRAM_ALLOWED_USER_ID` | الزامی | فقط یک شناسهٔ عددی مجاز برای هر سمت؛ بدون پیش‌فرض عمومی |
| `BALE_BOT_USERNAME` / `TELEGRAM_BOT_USERNAME` | الزامی | نام کاربری ربات متناظر، با یا بدون `@` |
| `BALE_PRIVATE_CHAT_ID` | شناسهٔ کاربر مجاز بله | چت خصوصی پین‌شدهٔ همان کاربر؛ در صورت تفاوت با تست محلی تأیید شود |
| `DATA_ENCRYPTION_KEY` | الزامی | کلید ثابت base64 با ۳۲ بایت |
| `DATA_DIR` | `./data` | دیسک محلی ماندگار |
| `POLL_TIMEOUT_SECONDS` | `25` | بازهٔ مجاز ۱ تا ۵۰ ثانیه |
| `MAX_FILE_MIB` | `20` | بازهٔ مجاز ۱ تا ۲۰ |
| `MAX_PENDING_JOBS` | `1000` | مجموع کارهای معوق؛ ظرفیت متناسب با دیسک بگذارید |
| `METADATA_RETENTION_DAYS` | `7` | فقط متادیتای پایان‌یافته و نگاشت پاسخ |
| `SEND_INTERVAL_MS` | `1100` | فاصلهٔ ارسال هر بات؛ حداقل ۱۰۰۰ میلی‌ثانیه |
| `REMOVE_EXISTING_WEBHOOK` | `false` | تغییر صریح برای جایگزینی webhook قبلی |

خطای `auth`: توکن محلی رد شده است. `bot_username_mismatch`: توکن با نام مورد انتظار یا نتیجهٔ معتبر `getMe` تطابق ندارد. `conflict`: polling/وبهوک دیگری فعال است. `configuration_or_storage_error`: `.env`، کلید قبلی، مسیر داده و فضای دیسک را بررسی کنید. `network` و `transient`: تلاش خودکار ادامه دارد. `queue_capacity_reached`: صف پر است و پیام تأییدنشده باقی می‌ماند. پایگاه را برای رفع خطا پاک نکنید؛ ممکن است پیام معوق داشته باشد.

## آزمون پذیرش واقعی

۱. با هر دو حساب مجاز Start کنید؛ حساب سوم و گروه نباید هیچ محتوایی به طرف دیگر برسانند.
۲. در هر دو جهت متن فارسی و ایموجی، عکس، ویس، صوت، ویدئو، سند، کپشن، پاسخ و ویرایش را امتحان کنید.
۳. استیکر، ویدئوی دایره‌ای، آلبوم، موقعیت زنده، نظرسنجی، فایل مرزی و نوع پشتیبانی‌نشده را با قرارداد بالا مقایسه کنید.
۴. ارتباط موقت مقصد را قطع کنید؛ دریافت و ذخیرهٔ سمت سالم، پاسخ `/status`، سپس تخلیهٔ صف پس از وصل‌شدن را بررسی کنید.
۵. restart وسط صف و وسط پیام چندقسمتی را آزمایش کنید؛ تکرار در مرز پاسخ نامطمئن ممکن است.
۶. فضای دیسک، backup و بازیابی با همان کلید را با دادهٔ غیرحساس تمرین کنید.

آزمون‌های خودکار این پروژه mock هستند و به ربات واقعی پیام نمی‌فرستند. گزارش آزمون دقیق در [VALIDATION.md](./VALIDATION.md) ثبت می‌شود.
